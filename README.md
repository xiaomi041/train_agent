# 🚄 AI 火车票查询助手（12306 官方接口版）

基于 **12306 官方余票接口 + DeepSeek 大模型 + Multi-Agent 架构**的智能火车出行规划助手。输入出发站、到达站和日期，即可获取直达/中转全部车次的余票与票价，并自动推荐**总票价最低**、**全程耗时最短**的最优路线；同时支持乘车规则类问题的即时问答。

## ✨ 功能特性

- **🔍 12306 官方余票接口逆向解析** —— 免费、无限制调用，直接解析官方接口返回的车次、到发时刻、历时及 7 类席别（商务座/一等座/二等座/软卧/硬卧/硬座/无座等）余票与票价，无需任何付费第三方 API
- **🗺️ 图搜索最优路线** —— 内置全国主要枢纽站图，遍历所有可行中转组合，枚举「票价最低」「耗时最短」及 Top5 候选方案（直达 + 单点中转）
- **🧭 多约束规划** —— 预算 / 总耗时 / 出发时段 / 到达时段 / 换乘次数 / 席别偏好一起卡，输出可行集、被排除方案的具体原因，以及价格-耗时前沿
- **🎯 盯票 Agent** —— 目标持久化为约束集，后台按间隔轮询，命中即通知；无票时逐级放宽（中转 → 日期 → 席别 → 预算），并留下每轮决策记录
- **🤖 Multi-Agent 架构** —— 主 Agent（DeepSeek + ReAct 多步推理）负责查票规划与工具调度；独立评审 Agent 对候选方案二次挑刺（换乘等待时间、余票充足度、站名一致性、价格对比完整性），保证推荐质量
- **💬 自然语言多轮对话** —— 模糊指令自动拆解（如"帮我安排国庆回家""明天重庆到杭州最省钱的路线"），Function Calling 调度工具，多轮追问自动结合上下文（"那换乘呢""下午的车呢"）
- **📚 RAG 乘车知识库** —— 内置退票/改签/儿童票/学生票/购票时间等乘车规则，本地 Embedding（`bge-small-zh-v1.5`）向量化 + 余弦相似度检索，规则类问题即时准确回答，不凭记忆编造
- **⚡ Streamlit 聊天式界面** —— 表单直查（出发/中转/到达 + 日期，支持车站⇄城市）与自由对话双通道

## 🏗️ 系统架构

```
用户 ──> Streamlit 界面 ──> 主 Agent（DeepSeek + ReAct 推理）
                              │  思考 → 行动 → 观察 → 回答
                              ├── 工具① query_train_ticket   ──> 12306 官方余票接口
                              ├── 工具② calc_transfer_scheme ──> 枢纽站图搜索 · 中转组合枚举
                              ├── 工具③ search_knowledge     ──> 本地向量库（bge-small-zh 余弦检索）
                              ├── 工具④ review_plan          ──> 独立评审 Agent 挑刺
                              └── 工具⑤ get_today            ──> 相对日期解析
```

- **主 Agent**：DeepSeek + Agno，注册 5 个工具，强制 ReAct 多步推理（查直达 → 枚举中转 → 独立评审 → 综合推荐）
- **评审 Agent（Critic）**：独立 DeepSeek 实例，只负责对候选方案挑刺，不参与查票
- **数据层**：12306 官方余票接口（实时数据）、`stations.json`（站点缓存）、`train_knowledge.md`（知识库源，启动时自动向量化）

## 🎯 盯票 Agent（常驻模式）

原来的用法是「问一句、查一次、给个结果」。任务单薄的地方在于：**买票的难点不是查一次，而是盯到有票为止**。
`watch.py` 把它变成一个有状态、会降级、会放弃的常驻任务：

```python
from watch import Goal, Watcher, Store

goal = Goal(origin="十堰", dest="哈尔滨", date="2026-11-20",
            budget=500, max_minutes=840, arrive_before="22:00",
            seat_prefs=["硬卧", "二等座"], interval_sec=300)
store = Store()
store.save_goal(goal)
Watcher(goal, fetcher=real_fetcher, store=store).start()   # 后台轮询
```

三条判据都有代码落点（也是 `test_watch.py` 的断言对象）：

| 判据 | 落点 | 失败会怎样 |
|---|---|---|
| 目标可验证 | `Goal` 是约束集，`check(scheme, goal)` 返回违规项 | 不会被"看起来差不多"的方案骗过去 |
| 多步自主推进 | `decide()` 按本轮观察决定：命中 / 降级 / 等待 / 放弃 | 路径随余票变化，不是固定流水线 |
| 失败自恢复 | `tick()` 区分四类失败 | 暂时性→退避重试；数据缺失→换查法；目标不可达→逐级放宽；内部错误→兜底不编造 |

逐级放宽的顺序（`relax_level` 0→4）：允许中转 → 日期前后浮动 → 席别不限 → 预算 +20% / 到达时段放宽。
每一级都会留下事件记录（`watch.db` 的 `events` 表），界面上可以逐条看它"为什么这么判"。

离线跑测试：

```bash
python test_watch.py      # 33 条断言，秒级完成
python watch.py demo      # 看一遍「无票 → 降级 → 命中」的完整决策链
```

## 🧭 多约束规划（不只是「最便宜」和「最快」）

原来界面上两个按钮分别算「票价最低」和「耗时最短」——真实需求往往不是这两者，而是
「800 块以内、周五下班后走、最多换一次、到了别太晚」。`planner.py` 把这变成一个**约束求解**：

```python
from planner import Constraints, plan

cons = Constraints(budget=800, max_minutes=600,
                   depart_after="18:00", arrive_before="23:00",
                   max_transfers=1, seat_prefs=["二等座", "硬卧"])
res = plan("北京", "上海", "2026-11-20", cons)
print(res.picks_table())    # 💰 最便宜 / ⚡ 最快 / ⚖️ 折中，每条带取舍说明
print(res.excluded_text())  # 被排除的方案 + 具体原因（超预算 / 到达太晚 / 席别不符）
```

三个和「查询」不一样的地方：

1. **无解会说无解**，不会硬凑一个「看起来差不多」的方案给你。
2. **排除要有理由**：每个被排除的方案都归到具体违规项，不会悄悄消失。
3. **价格-耗时前沿**：只保留「再快就得更贵」的那几个点，被支配的方案直接不展示。

离线测试（26 条断言，覆盖六类约束、前沿计算、无解、通知失败降级）：

```bash
python test_planner.py
```

## 🔔 通知（盯票命中 → 手机）

盯票命中或放弃时调 `notify.send()`，**主通道是 ntfy**（手机装个 App 订阅一个 topic 就完），
不依赖任何其他服务：

```python
import notify
notify.send("盯票命中：G1234 二等座 ¥553", dedupe_key="g1|G1234")  # dedupe_key 防重复
notify.pending()   # 队列里还有几条没发出去
notify.drain()     # 补发
```

三个通道各自独立，配了哪个走哪个：

| 通道 | 开启方式 | 说明 |
|---|---|---|
| ntfy（推荐） | `NOTIFY_NTFY=<topic>` | 主通道，手机 App 订阅；自建服务器用 `NOTIFY_NTFY_SERVER` |
| 群机器人 | `NOTIFY_WEBHOOK=<url>` | 飞书 / 钉钉 / 企业微信，按域名自动选载荷 |
| 提醒服务（可选） | `REMIND_URL=<url>` | 投给 PersonalAI 的 `/remind`，能进它的提醒列表；**留空即完全关闭** |

> **2026-11-20 的改动**：以前 `REMIND_URL` 默认指向 personal-ai 的提醒服务，等于盯票的通知
> 依赖另一个项目活着 —— 那个项目重启的几秒里通知投不进去，它界面上的问题也会牵连过来。
> 现在默认走 ntfy，`REMIND_URL` 留空就完全不碰它；想联动时显式配一行即可。

失败**不会阻塞决策**：只有失败过的通道会进本地队列（`notifications.jsonl`），
下次 `drain()` 只重试这些，成功的不重发（否则手机会收到两遍）。
一个通道都没配时直接 `skipped`，不写队列。

```bash
python notify.py --ntfy "测试：手机能不能收到"   # 单独验 ntfy
python notify.py --push "测试：群机器人"        # 单独验 webhook
python notify.py --pending                     # 队列里积了几条
python notify.py --drain                       # 手动补发一次
```

## 🎫 出票卡片与群机器人推送

### 为什么不自动下单

真自动下单需要三样东西：12306 登录票据、短信/滑块验证、支付密码。前两个能做但违反
12306 用户协议（封的是你本人的实名账号），第三个不该放在这个项目里。

所以做的是**半自动里最安全的一档**：命中之后，把「下一步」压缩到一次点击。

### 出票卡片

盯票命中后，任务卡片上会出现：

- **🎫 去 12306 预订（只剩点「预订」）** —— 官方查询页深链，日期、起终点已经填好
- **📋 出票信息（可复制发给同伴）** —— 车次 / 时间 / 席别 / 价格 / 换乘点，一段纯文本

深链形如 `kyfw.12306.cn/otn/leftTicket/init?linktypeid=dc&fs=北京南&ts=上海虹桥&date=2026-11-29`，
就是 12306 网页版自己在用的那套查询参数。

### 群机器人推送（飞书 / 钉钉 / 企业微信）

在 `trainAI/.env` 里填一行就开通：

```bash
NOTIFY_WEBHOOK=https://open.feishu.cn/open-apis/bot/v2/hook/xxxx
```

三家字段名不一样（飞书 `msg_type/content.text`，钉钉与企业微信 `msgtype/text.content`），
`notify.py` 按域名自动选载荷。

两个容易踩的点，`test_push.py` 都锁住了：

1. **HTTP 200 不等于成功**。机器人经常回 `200 + {"code":19001}`，只看到 200 会以为发成功了。
   现在检查返回体里的 `code/errcode/StatusCode`。
2. **失败不能影响主流程**。推送挂了只是少一条消息，盯票决策照常；失败照旧进 `notifications.jsonl` 队列。

单独验证通不通（不写提醒表）：

```bash
docker compose exec -T train-ai python notify.py --push "测试：来自 trainAI"
```

> 注意：钉钉机器人默认有「自定义关键词」安全设置，消息里必须包含你设的关键词，
> 否则会返回 `310000`。我们的消息里固定有「盯票命中」，如果你的关键词不是这个，改一下关键词即可。

### ntfy：不需要任何审批的推送

飞书/钉钉的「自定义机器人」在部分账号（个人版、或组织关闭了该能力）里根本没有入口——
表现为「添加机器人」页搜索「自定义」返回空。这时候用 ntfy 最省事：

1. 手机装 **ntfy**（App Store / 应用商店搜 `ntfy`）
2. App 里 `+` → 订阅 topic，起一个别人猜不到的，如 `dingpiao-cjh-8f3k2`
3. `trainAI/.env` 填一行：

```bash
NOTIFY_NTFY=dingpiao-cjh-8f3k2
```

4. 重建容器并按需验证：

```powershell
docker compose up -d --force-recreate train-ai watch-worker
docker compose exec -T train-ai python notify.py --ntfy "测试：来自 trainAI"
```

- 默认走公共服务器 `https://ntfy.sh`，自建就加 `NOTIFY_NTFY_SERVER=https://push.example.com`
- 标题走 ASCII 头（HTTP 头不能放中文），正文是 UTF-8，中文没问题
- 浏览器打开 `https://ntfy.sh/<topic>` 也能直接看到消息，方便调试
- 和 webhook **可以同时开**，两条通道互不影响

### 双通道

配置了 webhook 就是**两条腿走路**：提醒表（打开页面能看到弹窗）+ 群消息（手机秒到）。
没配 webhook 就退回原来的单通道。

## 🔁 通知发失败会自动补发

盯票命中的通知有多个出口（ntfy / 群机器人 / 可选提醒服务），任何一条失败都会被写进
`notifications.jsonl` 队列，但**光写队列不够**——以前只有手动 `python notify.py --drain`
才会重发，等于"任务显示命中了，人永远没收到"。

现在 `watch-worker` 每 300 秒（`WATCH_DRAIN_SECONDS`）顺手补发一次，启动时也立刻补一次。
队列文件放在 `./data/train` 卷里（`NOTIFY_QUEUE=/app/data/notifications.jsonl`），
容器重建也不会丢。

补发**只重发失败的那条通道**：payload 里记了 `channels`，比如「提醒服务挂了但 ntfy 通了」
就只会重新 POST 提醒服务，不会让手机收到第二遍同样的消息。

```bash
# 看还有几条没发出去
docker compose exec -T watch-worker python notify.py --pending
# 手动补发一次（正常情况下 worker 会自己发，这条用于排查）
docker compose exec -T watch-worker python notify.py --drain
```

实测链路（解耦后，2026-11-20）：往队列里塞一条 → `drain` 返回 `{'sent': 1, 'left': 0}` → ntfy 手机端收到，`reminders` 表**不再**新增行。

### 通知去重（NOTIFY_DEDUPE_SECONDS）

同一次命中被两个 tick 各通知一遍时，界面上会出现两条一模一样的提醒（真实发生过）。
现在 `notify.send(..., dedupe_key=...)` 用文件记录 keys（默认窗口 600 秒），同 key 只发一次；
`Watcher` 命中时传的 key 是 `任务id|车次|席别|日期|开点`，换车次/换日期仍会正常提醒。
发过的 key 存 `notify_sent.jsonl`（与队列同目录），过期记录在下次检查时顺手清掉。


## 🛰 常驻盯票进程（watch_worker.py）

`Watcher.start()` 的轮询线程挂在 Streamlit 的 `session_state` 上，**关掉网页线程就没了**。
所以后台盯票由独立进程承担，与提醒服务同构：

```bash
python watch_worker.py            # 常驻
python watch_worker.py --once     # 只跑一轮（调试/CI）
```

设计要点：

1. **共用一个库**：Web 端新建任务写 `watch.db`，worker 直接读，不需要任何消息队列。
2. **自适应退避**：连续「等待」时把间隔放大到 1.5×、2.25×……最多 4 倍（`WATCH_BACKOFF_MAX`）；
   一旦命中或升档立即复位。理由：两小时的没票窗口里每 5 分钟查一次，只是给 12306 发无效请求。
3. **没票 ≠ 放弃**：`decide()` 只有在"有候选但怎么放宽都不满足"时才放弃；一条都没有时先扩搜（前两级），
   到第 2 级就转为长期等待 —— 昨天没票今天可能有票，这才是盯票的意义。
4. **单轮上限**：`WATCH_MAX_PER_ROUND`（默认 20）防止任务堆积时一次打满接口。

## 🧭 中转枢纽怎么挑（geo.py）

以前是 `hubs[:3]` —— 取列表里前三个站，和乘客从哪到哪毫无关系。现在按"是否顺路"筛：

| 判据 | 含义 | 例子（北京→上海） |
| --- | --- | --- |
| 沿线路进度 `t` | 枢纽在线路上的位置，要求 `0.12 ≤ t ≤ 0.92` | 天津 `t≈0.10` → 太近，排除（刚上车就下车） |
| 横向偏移比 | 垂直于线路的距离 / 全程，要求 ≤ 0.25 | 郑州 `0.43` → 方向不对，排除 |
| 绕行比 | `(起点→枢纽 + 枢纽→终点 − 全程) / 全程`，要求 ≤ 0.6 | 长沙 `1.09` → 兜底拦截 |
| 排序 | `绕行比 + 0.6×|t−0.5|` | 偏向"中段且几乎不绕路"的枢纽 |

坐标是**城市级近似值**（精确到 0.01°），只用于判断方向，不做测地计算；
认不出的城市会回退到原始顺序，不会因为查不到坐标就一个中转都不试。

## 🔀 多段中转（route.py）

以前最多只会拼两段（直达 + 一个枢纽）。现在支持 **A→h1→h2→B** 三段：

| 规则 | 取值 | 为什么 |
| --- | --- | --- |
| 换乘最短间隔 | 30 分钟（`TRANSFER_MIN_GAP_MIN`） | 接口不告诉你是否同站，取保守值；10 分钟那种拼出来也赶不上 |
| 换乘最长间隔 | 6 小时（`TRANSFER_MAX_GAP_MIN`） | 更久不如在中间城市过夜换方案 |
| 每段候选上限 | 25 班（`TRANSFER_SEG_KEEP`） | 三段全排列是 O(n³)，不剪枝会有几万组合 |
| 链候选上限 | 40 条（`TRANSFER_CHAIN_KEEP`） | 只留最早到达 / 最便宜的 |

**按城市拼、不按车站拼**：12306 的接口把站名归一到城市，在车站级别拼会 9×5 爆炸，
而且拼出来的"换乘"现实中未必同站。

**只在必要时才跑**：`max_transfers >= 2` 且盯票放宽到第 2 级（说明直达和一次换乘都没票）。
界面上「换乘」选「最多换 2 次（多段）」即开启。

实测（太原 → 厦门，2026-11-29，枢纽 武汉/合肥/南昌）：

```
请求 9 次 / 耗时 2.5 s / 可行链 40 条
2026-11-29 21:48-11:57 硬卧/硬卧/二等座 ¥622（换乘 2 次）
  V1398 太原→合肥 21:48-12:55 ｜ N221 合肥→南昌 18:50-01:21 ｜ D2361 南昌西→厦门北 07:20-11:57
```

**跨日要按绝对时间累加**：第一版用「同一天 + 必要时 +1 天」算总耗时，三段跨两天时会把
38 小时算成 14 小时。现在沿链推 `datetime`，`test_route.py` 里有一条「跨两天总耗时 > 24 小时」
专门锁死这个。

```bash
python test_route.py     # 23 条断言，全离线，不需要网络
```

### 仍然做不到的

- 换乘间隔是**固定窗口**，不知道是不是同站换乘、要不要出站（12306 不给这个数据）。
- 枢纽两两组合仍然是"先按顺路挑 3 个再组合"，不是全网搜索；真要全网搜就是图算法 + 时刻表了。
- 只算"最早到/最便宜"，不排出"在这座城市中转顺便吃个饭"这种人类约束。

## 📈 性能实测（bench_train.py）

数字来自容器内打真实 12306 接口，场景固定为 `北京 → 上海 2026-11-25`，复跑命令：

```bash
docker compose cp trainAI/bench_train.py train-ai:/app/bench_train.py
docker compose exec -T train-ai python bench_train.py
```

| 指标 | 数值 | 说明 |
| --- | --- | --- |
| 单次余票查询 | 75 ms（P50）/ 482 ms（P95） | 5 次采样，网络抖动明显 |
| 规划（3 枢纽） | 1 次请求 / 0.27 s / 84 候选 | 直达已可满足，未触发中转 |
| 规划（6 枢纽） | 5 次请求 / 2.34 s / 7785 候选 | 进入中转枚举 |
| 真实重约束规划 | 7 次请求 / 3.29 s / 15026 候选 → 116 可行 | 预算 800 元、总耗时 600 分钟、最多 1 次换乘 |
| 一次盯票 tick | 3 次请求 / 1.21 s | 修复前是 **135 次 / 54.6 s** |

### 那次 45 倍的修复

测量时发现一次 tick 要发 135 次请求、跑 54.6 秒。查下来是 `real_fetcher` 把城市展开成
同城车站逐个查：北京 9 个站 × 上海 5 个站 = 45 个组合。

但 12306 的余票接口**自己就把站名归一到城市**——查「北京南→上海虹桥」返回的仍是北京/北京丰台/
北京南 三个站的全部车次。所以那 45 次请求拿到的是 45 份一模一样的数据：请求数 ×45、
耗时 ×45、候选里全是重复项（候选数被灌到 33306，真实规模约 1.5 万）。

改为直接按城市查 + 按 `(车次, 席别, 日期)` 去重后：135 次/54.6 s → **3 次/1.2 s**。
新增 4 条断言锁死这个行为（`test_watch.py` 的第 11、12 组）。

### 已知开销

- 单次 tick 最短 3 次请求（直达 1 + 中转 2 段 × 1 枢纽）。放宽级别越高、日期窗口越大，请求数线性增长。
- 接口无官方配额说明，所以默认检查间隔 20 秒、退避上限 4×，宁可慢也不要把 IP 打进去。


## 🕰 长时间跑、多个任务、多个人（bench_load.py / bench_longrun.py）

盯票是**长期在跑**的东西：一直开着、任务会积累、可能还不止你一个人在开。所以这三件事各做了一次测量。

复跑命令：

```bash
docker compose cp trainAI/bench_load.py train-ai:/app/bench_load.py
docker compose cp trainAI/bench_longrun.py train-ai:/app/bench_longrun.py
docker compose exec -T train-ai python bench_load.py
docker compose exec -T train-ai python bench_longrun.py --days 30 --goals 10
```

### 每条事件多大、30 天会涨到多少

`watch.db` 里一次「等待/降级/命中」就是一条事件，实测 **156 字节/条**。

| 策略 | 事件行数 | 库大小 | 写入耗时 | 查 50 条 |
| --- | --- | --- | --- | --- |
| 不裁剪 | 86400 | 13848 KB | 8.4 s | 0.19 ms |
| 每任务留 200 条 | 2050 | **388 KB** | 18.9 s | 0.12 ms |

10 个任务跑满 30 天 = 8640 轮。不裁剪会留下 86400 行 / 13.5 MB；每任务留 200 条后是
2050 行 / **388 KB**，文件小 **36 倍**、行数少 42 倍。默认 `WATCH_PRUNE_SECONDS=1800` 裁一次。

这里踩了三个坑，都写进代码注释了：

1. 第一版裁剪用 `DELETE ... WHERE id NOT IN (SELECT ...)`，30 天写入从 8 s 拖到 **81 s**——
   子查询每删一批就把全表扫一遍。改成「先查阈值 id，再按 id 删」。
2. SQLite 默认 `auto_vacuum=0`：删了行只是把页标记为空闲，**文件不会变小**。裁掉 42 倍的行之后
   文件反而更大。所以建库时设 `INCREMENTAL`，并在裁剪后 `incremental_vacuum`。
3. WAL 文件不 truncate 会一路长到 30 MB。裁剪后补一次 `wal_checkpoint(TRUNCATE)`。

### 一次检查要花多少时间

10 个任务一轮的调度本身 **12.6 ms/条 → 0.2 ms/条**（换成 WAL + `synchronous=NORMAL` 之后），
写 2880 条事件从 19.3 s 降到 **0.22 s（87 倍）**。也就是说调度开销可以忽略，
真正的成本是 12306 的请求往返。

### 多个任务同时盯：要不要并发

单个任务的成本是**等待网络**，不是算力，所以串行跑很亏。用 20 个任务、fetcher 只 sleep 模拟网络测得：

| 单次查询耗时 | 串行 | 2 路 | 4 路 | 8 路 |
| --- | --- | --- | --- | --- |
| 300 ms | 6.02 s（3.32 任务/s） | 3.01 s | **1.51 s（13.28 任务/s）** | 0.90 s |
| 50 ms | 2.02 s（9.89 任务/s） | 0.51 s | **0.26 s（77.9 任务/s）** | 0.17 s |

默认 `WATCH_CONCURRENCY=4`：4 倍提升，再往上收益递减（8 路只比 4 路快 1.7 倍），
而且越并发越容易撞 12306 的限流。线程池是**复用**的——每轮新建一个线程池在 Windows 上要 60 ms，
比干活本身还贵。

### 多个人同时用

口令是共享的，但**任务按人隔离**：

- 登录时填「你的名字」→ 存进 `st.session_state.owner`（留空就是 `default`）。
- 所有 `goals` / `events` / `bookings` 都带 `owner` 列，查询默认按 owner 过滤，别人的任务你看不到。
- 每人同时最多 5 个在建任务（`WATCH_MAX_ACTIVE`），防止一个人把队列占满。
- 老库会自动 `ALTER TABLE ... ADD COLUMN owner DEFAULT 'default'`，不用手动迁移。

这套隔离够用但不等于「多租户」：口令还是同一个，谁都能用任意名字登录看**自己的**记录。
真要给外人用，得换 `st.login` 或每用户独立口令。

### 🎟 订票记录 = 长记忆

任务命中后可以点「✅ 我买了这趟」，记进 `bookings` 表（日期/车次/席别/票价/记录时间）。
之后聊天时，`recent_context(owner, 3)` 会把最近 3 条压成一句话塞进提示词：

```
你以前的订票记录（供参考，不必复述）：
2026-11-21 07:20 南昌西→厦门北 D2361 二等座；2026-11-20 06:18 北京南→上海虹桥 G547 二等座
```

这样「再帮我买个回家票」不用每次从头问。记录长期保留（不参与裁剪），但**只做提示、不参与
自动决策**——它不会让 Agent 自作主张跳过预算约束。

## 🧠 放宽哪一项：规则 vs 模型（`decider.py` + `bench_decide.py`）

盯票遇到「有候选但都不满足」时要决定放宽哪个约束。原来按固定顺序开：
允许中转 → 日期浮动 → 不限席别 → 预算上浮 → 耗时上浮 → 不限到达时段。
问题是顺序跟实际卡点无关：用户明明被预算卡住，它先去放开一个不相关的维度，
于是多跑几轮、多查几次接口，而用户的容忍度是有限的——开到第 4 项才发现该放预算。

`decider.py` 把这一步交给模型（只给它约束、已放宽项、最优候选差在哪，约 400 token）。
**2026-11-20 起模型版是默认**（`DECIDE_MODE=llm`）：它是"决策权在模型"这条判据的落点，
默认关掉等于默认承认自己是规则引擎。为了不让它变成"每小时烧钱"，加了三道闸：

| 闸 | 行为 | 默认 |
|---|---|---|
| 局面缓存 | 同一组约束 + 同一批违规项只问一次模型（盯票的常态是"局面几十分钟不变"） | 256 条 LRU |
| 单任务配额 | 每个任务每小时最多 6 次模型决策，超了退回规则，任务不停摆 | `DECIDE_MAX_CALLS=6` |
| 异常即退回 | 模型挂、返回不是 JSON、配额用完 → 一律按固定顺序 | 硬编码 |

六个场景的对照（`python bench_decide.py`）：

| 场景 | 卡在哪 | 规则版 | 模型版 |
|---|---|---|---|
| money | 620 元 > 预算 600 | 4 项、8 次请求 | **1 项、2 次** |
| seat | 一等座不在偏好里 | 3 项、6 次 | **1 项、2 次** |
| arrive | 00:30 到，超出时段 | 6 项、12 次 | **1 项、2 次** |
| date | 当天没票，次日有 | 2 项、4 次 | **1 项、2 次** |
| wait | 只是没放票，第三轮会来 | 2 项、5 次 | **1 项、4 次** |
| hopeless | 全都放开也不够 | 6 项→放弃 | 8 轮→放弃 |

合计：**放宽 23 → 11 项（−52%）、请求 47 → 26 次（−45%）**，命中都是 5/6；
代价是 11 次真实模型调用 + 6 次缓存命中，合计约 **¥0.0085**（加了缓存之前的同样对照是
17 次调用、¥0.0130，缓存省掉 35%）。

三条保护（都测过）：
1. 模型返回非法值或抛异常 → 退回固定顺序，盯票不停（`pick_dim` 里 catch 后 fallback）；
2. 模型连续说「先等等」超过 `DECIDE_MAX_WAITS`（默认 3）次 → 收回决策权按顺序放宽，
   避免任务永远停在原地不动；
3. 每小时 6 次配额用完 → 本轮直接按规则开，并在日志里写一行"配额已用完"。

## ✏️ 改约束：人中途改主意要接得住

任务建完不是铁板一块。`watch.edit_goal(goal, **changes)` 支持改预算 / 日期 / 席别 / 时段 /
换乘次数 / 间隔，界面在每张任务卡片上的「✏️ 改约束」里。

关键不是"能改"，而是**改完清空放宽状态**：旧的放宽记录是"为了让这次搜索命中而降级过什么"，
约束一变它就过期了（原来超预算 20 元，预算调高后就不超了），继续沿用会让判定偏松。
另外 `done` / `failed` 的任务改约束会被复活成 `active`——用户改约束的意思通常是"再盯一次"。

白名单之外的字段（`status` / `owner` / `id`）会抛 `KeyError`：界面顺手改掉状态会绕过
所有状态机逻辑，这类"方便"迟早变成 bug。

## 🔁 反馈闭环：同一个错误犯两次之后，策略自己要改

前两步分别是"这一轮放宽哪一项"和"人中途改主意"。第三步是：**误报两次之后，系统自己收紧**。

数据来源是用户点的「🙅 不是我要的」——但一条反馈只说"这次不对"，没说哪里不对，所以用
同一任务最近一次「命中」事件里记录的席别来归因。规则（`policy.py`）：

- 同一线路（起点→终点）同一席别误报 ≥ `POLICY_WRONG_THRESHOLD`（默认 2）次；
- 新建任务时默认剔除该席别，并把 `strict_seat` 打开；
- 界面给一句提示，写清"依据是哪几次、怎么改回来"。

只收紧、不放松：自动放宽会掩盖问题（结果更差但没人发现），而且会让策略变成黑箱。

对照实验（`python bench_loop.py`，10 轮，用户其实只要硬卧、但偏好里写的是「二等座、硬卧」）：

| 组 | 误报次数 | 命中率 | 总检查 | 每轮买到 |
|---|---|---|---|---|
| A 无闭环（只记不改） | 10 | 100% | 10 | 二等座 ×10 |
| B 有闭环（≥2 次收紧） | **2** | 100% | 10 | 二等座 ×2 → 硬卧 ×8 |

**同一个错误从 10 次降到 2 次（−80%）**，命中率不变——闭环改的是"买什么"，不是"能不能买到"。
剩下的 2 次是阈值本身的代价（前两次误报必须发生，系统才知道要收紧）。

## 📊 真实使用的度量（`watch.Store.feedback` / `watch.Store.stats`）

「命中率 100%」这种话在自己造的测试集上很容易写，难的是**有人真的在用**时有数字可看。
接口两个：

```python
store.feedback(goal_id, "good" | "wrong", note="")   # 用户对这次命中的评价
store.stats(days=7, owner=None)                      # 这段时间发生了什么
```

`stats()` 返回的是事实，不是打分：

| 字段 | 含义 | 为什么值得看 |
|---|---|---|
| `goals` / `status` | 任务数与 盯票中/已命中/已放弃/已停止 | 用户是真的建了任务，还是点了一下就走 |
| `checks` | 累计检查次数（= 各任务 `attempts` 之和） | 直接对应接口压力，也是「它真的在后台跑」的证据 |
| `hit_rate` | 已命中 /（已命中 + 已放弃） | 太低了说明约束太紧或网络太差 |
| `avg_ticks_to_hit` | 命中任务平均查了几轮 | 涨说明票越来越难抢，或退避太激进 |
| `avg_dims_at_hit` | 命中时平均放宽了几项 | 接近 6 说明几乎全靠放宽才成，约束形同虚设 |
| `wrong` / `good` | 用户点的「不是我要的 / 就是这趟」 | **误报率**，比命中率更能说明阈值合理与否 |
| `bookings` / `owners` | 订票记录数、使用者数 | 真实使用规模的唯一硬指标 |

界面里是「📊 使用统计（最近 7 天）」这块，任务卡上多了两个按钮（👍 就是这趟 / 🙅 不是我要的）。

坑：`stats()` 用 `Goal.from_json(spec)` 还原每条任务，所以统计口径与产品完全一致
（比如"放宽了几项"用的是同一套 `relax_dims()`，不会出现两处各算一套）。

## ⏱ 长周期观察（心跳 + `observe.py`）

盯票这种东西，**头十分钟的日志说明不了任何问题**。真正要看的是：跑一天之后它还在不在转、
间隔有没有按退避放大、事件表有没有被裁干净。这两件事以前只能靠手动 `docker logs` 翻，
现在拆成「进程自己报数」+「脚本摊开历史」两块。

### 1. 进程每 10 分钟打一行心跳

```
2026-11-20 01:10:07 INFO  [watch_worker] 心跳：运行 0.0 小时｜轮次 1｜tick 2 次｜盯票中 2 个｜事件 38 条｜库 48.0 KB
```

四个问题各对应一段：`盯票中 N 个` 说明还有活在干、`事件 E 条 / 库 B KB` 说明存储有没有失控、
`轮次/tick` 说明主循环是不是真在转、`运行 X 小时` 说明这次进程活了多久。

间隔可用环境变量调：`WATCH_HEARTBEAT_SECONDS=600`（0 关闭心跳）。

> 心跳的 `运行小时数` 是**本进程**的存活时间。机器睡眠、容器重启后它从 0 开始，
> 但任务状态在 SQLite 里不会丢 —— 所以「断过多久」要看日志时间戳，不能看这个数。

### 2. `observe.py` 把事件摊成时间线

```bash
docker compose exec -T watch-worker python observe.py --days 1
docker compose exec -T watch-worker python observe.py --goal 414371e2
```

输出每个任务的：事件条数、命中/放弃次数、间隔中位/最大/平均、放宽档位轨迹、最近三条事件，
以及**超过 1 小时的空洞**（这是机器睡眠/容器被停的直接证据）。

实测样例（本地 5 个任务、38 条事件）：

```
[6fd8063c] 深圳→乌鲁木齐 2026-11-25｜active｜attempts=32｜事件 32 条｜命中 0｜放弃 0
    间隔：中位 987s｜最大 4860s｜平均 867s
    放宽档位：最高 2｜轨迹 22222222222222222222…
    ⚠ 有 1 段超过 1 小时没有事件（机器睡眠/容器停止）：
       11-20 00:51 距上一条 1.4 小时
```

最后一行是这套设施的意义所在：**不写这个检查，人会把「机器睡了 1.4 小时」误读成「盯票卡死了」**。

### 3. 一个反直觉的观察

`watch-worker` 重启后所有任务的计时器都会重置，所以重启后的第一轮会**立刻把所有任务查一遍**。
上面 `414371e2` 的事件间隔是 90 秒、而它的 `interval_sec=300`，就是这个原因。
观察日志时要先看有没有重启，否则会把重启误读成"退避没生效"。

### 4. 两天窗口的真实数据（2026-11-20 02:00）

`observe.py --days 2` 在容器内的原始输出（5 个任务、58 条事件、库 48 KB）：

| 任务 | 线路/日期 | 状态 | 检查 | 间隔中位/最大 | 轨迹 |
|---|---|---|---|---|---|
| `6fd8063c` | 深圳→乌鲁木齐 11-25 | 盯票中 | 41 | 664s / 4860s | 2 到顶 |
| `414371e2` | 深圳→乌鲁木齐 11-25 | 盯票中（重复样本） | 13 | 211s / 683s | 2 到顶 |
| `7d7857e3` | 北京→上海 11-23 | 已命中 | 1 | — | 0 |
| `b1521ae3` | 广州→长沙 11-22 | 已命中 | 1 | — | 0 |
| `93ed4138` | 遵义→重庆 11-19 | 已命中 | 1 | — | 0 |

`stats()`：任务 5｜检查 57｜命中率 100%｜平均命中轮数 1.0｜误报 0｜订票 0。

三条能从这个窗口读出来的事实：

1. **退避是单调的、且有上限**：`6fd8063c` 从 300s 一路涨到 1200s（`WATCH_BACKOFF_MAX=4`），
   之后稳定在 664s 中位——不是每轮都翻倍，命中/放宽时会被 `_backoff` 复位。
2. **最大间隔 4860s 不是退避失控**，是 00:51 那段 1.4 小时机器睡眠 —— 没有第 2 节的空洞检测，
   这个数会被误读成"退避疯了"。
3. **命中率 100% 是样本太小的假象**：4 次命中 0 次放弃，`checks=57 < 100`，
   `observe.py` 因此会明确打印"数据不足以下结论"。真要把这条写进简历，至少得跑到 100 次检查以上。

顺带做的一次运维清理：`414371e2` 与 `6fd8063c` 是同线路同一天的重复样本（都是早期造的），
双份请求对 12306 是白给的压力，已把前者标成 `stopped` 并在 `note` 里写清原因。
**同一线路同一日期留一个任务**，这条也写进了 `USER_GUIDE.md`。
