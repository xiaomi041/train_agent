# 🚄 AI 火车票查询助手（12306 官方接口版）

基于 **12306 官方余票接口 + DeepSeek 大模型 + Multi-Agent 架构**的智能火车出行规划助手。输入出发站、到达站和日期，即可获取直达/中转全部车次的余票与票价，并自动推荐**总票价最低**、**全程耗时最短**的最优路线；同时支持乘车规则类问题的即时问答。

## ✨ 功能特性

- **🔍 12306 官方余票接口逆向解析** —— 免费、无限制调用，直接解析官方接口返回的车次、到发时刻、历时及 7 类席别（商务座/一等座/二等座/软卧/硬卧/硬座/无座等）余票与票价，无需任何付费第三方 API
- **🗺️ 图搜索最优路线** —— 内置全国主要枢纽站图，遍历所有可行中转组合，枚举「票价最低」「耗时最短」及 Top5 候选方案（直达 + 单点中转）
- **🧭 多约束规划** —— 预算 / 总耗时 / 出发时段 / 到达时段 / 换乘次数 / 席别偏好一起卡，输出可行集、被排除方案的具体原因，以及价格-耗时前沿
- **🎯 盯票 Agent** —— 目标持久化为约束集，后台按间隔轮询，命中即通知；无票时逐级放宽（中转 → 日期 → 席别 → 预算），并留下每轮决策记录
- **🤖 Multi-Agent 架构** —— 主 Agent（DeepSeek + ReAct 多步推理）负责查票规划与工具调度；独立评审 Agent 对候选方案二次挑刺（换乘等待时间、余票充足度、站名一致性、价格对比完整性），保证推荐质量
- **💬 自然语言多轮对话** —— 模糊指令自动拆解（如"帮我安排国庆回家""明天重庆到杭州最省钱的路线"），Function Calling 调度工具，多轮追问自动结合上下文（"那换乘呢""下午的车呢"）
- **📚 RAG 乘车知识库** —— 内置退票/改签/儿童票/学生票/购票时间等乘车规则，本地 Embedding（`bge-small-zh-v1.5`）向量化 + 余弦相似度检索，规则类问题即时准确回答，不凭记忆编造
- **⚡ Streamlit 聊天式界面** —— 表单直查（出发/中转/到达 + 日期，支持车站⇄城市）与自由对话双通道

## 🏗️ 系统架构

```
用户 ──> Streamlit 界面 ──> 主 Agent（DeepSeek + ReAct 推理）
                              │  思考 → 行动 → 观察 → 回答
                              ├── 工具① query_train_ticket   ──> 12306 官方余票接口
                              ├── 工具② calc_transfer_scheme ──> 枢纽站图搜索 · 中转组合枚举
                              ├── 工具③ search_knowledge     ──> 本地向量库（bge-small-zh 余弦检索）
                              ├── 工具④ review_plan          ──> 独立评审 Agent 挑刺
                              └── 工具⑤ get_today            ──> 相对日期解析
```

- **主 Agent**：DeepSeek + Agno，注册 5 个工具，强制 ReAct 多步推理（查直达 → 枚举中转 → 独立评审 → 综合推荐）
- **评审 Agent（Critic）**：独立 DeepSeek 实例，只负责对候选方案挑刺，不参与查票
- **数据层**：12306 官方余票接口（实时数据）、`stations.json`（站点缓存）、`train_knowledge.md`（知识库源，启动时自动向量化）

## 🎯 盯票 Agent（常驻模式）

原来的用法是「问一句、查一次、给个结果」。任务单薄的地方在于：**买票的难点不是查一次，而是盯到有票为止**。
`watch.py` 把它变成一个有状态、会降级、会放弃的常驻任务：

```python
from watch import Goal, Watcher, Store

goal = Goal(origin="十堰", dest="哈尔滨", date="2026-11-20",
            budget=500, max_minutes=840, arrive_before="22:00",
            seat_prefs=["硬卧", "二等座"], interval_sec=300)
store = Store()
store.save_goal(goal)
Watcher(goal, fetcher=real_fetcher, store=store).start()   # 后台轮询
```

三条判据都有代码落点（也是 `test_watch.py` 的断言对象）：

| 判据 | 落点 | 失败会怎样 |
|---|---|---|
| 目标可验证 | `Goal` 是约束集，`check(scheme, goal)` 返回违规项 | 不会被"看起来差不多"的方案骗过去 |
| 多步自主推进 | `decide()` 按本轮观察决定：命中 / 降级 / 等待 / 放弃 | 路径随余票变化，不是固定流水线 |
| 失败自恢复 | `tick()` 区分四类失败 | 暂时性→退避重试；数据缺失→换查法；目标不可达→逐级放宽；内部错误→兜底不编造 |

逐级放宽的顺序（`relax_level` 0→4）：允许中转 → 日期前后浮动 → 席别不限 → 预算 +20% / 到达时段放宽。
每一级都会留下事件记录（`watch.db` 的 `events` 表），界面上可以逐条看它"为什么这么判"。

离线跑测试：

```bash
python test_watch.py      # 33 条断言，秒级完成
python watch.py demo      # 看一遍「无票 → 降级 → 命中」的完整决策链
```

## 🧭 多约束规划（不只是「最便宜」和「最快」）

原来界面上两个按钮分别算「票价最低」和「耗时最短」——真实需求往往不是这两者，而是
「800 块以内、周五下班后走、最多换一次、到了别太晚」。`planner.py` 把这变成一个**约束求解**：

```python
from planner import Constraints, plan

cons = Constraints(budget=800, max_minutes=600,
                   depart_after="18:00", arrive_before="23:00",
                   max_transfers=1, seat_prefs=["二等座", "硬卧"])
res = plan("北京", "上海", "2026-11-20", cons)
print(res.picks_table())    # 💰 最便宜 / ⚡ 最快 / ⚖️ 折中，每条带取舍说明
print(res.excluded_text())  # 被排除的方案 + 具体原因（超预算 / 到达太晚 / 席别不符）
```

三个和「查询」不一样的地方：

1. **无解会说无解**，不会硬凑一个「看起来差不多」的方案给你。
2. **排除要有理由**：每个被排除的方案都归到具体违规项，不会悄悄消失。
3. **价格-耗时前沿**：只保留「再快就得更贵」的那几个点，被支配的方案直接不展示。

离线测试（26 条断言，覆盖六类约束、前沿计算、无解、通知失败降级）：

```bash
python test_planner.py
```

## 🔔 通知联动（盯票命中 → 系统提醒）

盯票命中或放弃时，`notify.send()` 会把消息投递给 PersonalAI 的提醒服务（`/remind`），
由它落库并在你下次打开页面时弹出确认：

```python
import notify
notify.send("盯票命中：G1234 二等座 ¥553", at="")   # at 为空 = 马上
notify.pending()   # 队列里还有几条没发出去
notify.drain()     # 补发
```

投递失败**不会阻塞决策**：消息进本地队列（`notifications.jsonl`），下次补发。
口令通过 `REMIND_TOKEN`（或 `APP_PASSWORD`）传递，服务端未配置口令时容器内直通。


## 🎫 出票卡片与群机器人推送

### 为什么不自动下单

真自动下单需要三样东西：12306 登录票据、短信/滑块验证、支付密码。前两个能做但违反
12306 用户协议（封的是你本人的实名账号），第三个不该放在这个项目里。

所以做的是**半自动里最安全的一档**：命中之后，把「下一步」压缩到一次点击。

### 出票卡片

盯票命中后，任务卡片上会出现：

- **🎫 去 12306 预订（只剩点「预订」）** —— 官方查询页深链，日期、起终点已经填好
- **📋 出票信息（可复制发给同伴）** —— 车次 / 时间 / 席别 / 价格 / 换乘点，一段纯文本

深链形如 `kyfw.12306.cn/otn/leftTicket/init?linktypeid=dc&fs=北京南&ts=上海虹桥&date=2026-11-29`，
就是 12306 网页版自己在用的那套查询参数。

### 群机器人推送（飞书 / 钉钉 / 企业微信）

在 `trainAI/.env` 里填一行就开通：

```bash
NOTIFY_WEBHOOK=https://open.feishu.cn/open-apis/bot/v2/hook/xxxx
```

三家字段名不一样（飞书 `msg_type/content.text`，钉钉与企业微信 `msgtype/text.content`），
`notify.py` 按域名自动选载荷。

两个容易踩的点，`test_push.py` 都锁住了：

1. **HTTP 200 不等于成功**。机器人经常回 `200 + {"code":19001}`，只看到 200 会以为发成功了。
   现在检查返回体里的 `code/errcode/StatusCode`。
2. **失败不能影响主流程**。推送挂了只是少一条消息，盯票决策照常；失败照旧进 `notifications.jsonl` 队列。

单独验证通不通（不写提醒表）：

```bash
docker compose exec -T train-ai python notify.py --push "测试：来自 trainAI"
```

> 注意：钉钉机器人默认有「自定义关键词」安全设置，消息里必须包含你设的关键词，
> 否则会返回 `310000`。我们的消息里固定有「盯票命中」，如果你的关键词不是这个，改一下关键词即可。

### 双通道

配置了 webhook 就是**两条腿走路**：提醒表（打开页面能看到弹窗）+ 群消息（手机秒到）。
没配 webhook 就退回原来的单通道。

## 🛰 常驻盯票进程（watch_worker.py）

`Watcher.start()` 的轮询线程挂在 Streamlit 的 `session_state` 上，**关掉网页线程就没了**。
所以后台盯票由独立进程承担，与提醒服务同构：

```bash
python watch_worker.py            # 常驻
python watch_worker.py --once     # 只跑一轮（调试/CI）
```

设计要点：

1. **共用一个库**：Web 端新建任务写 `watch.db`，worker 直接读，不需要任何消息队列。
2. **自适应退避**：连续「等待」时把间隔放大到 1.5×、2.25×……最多 4 倍（`WATCH_BACKOFF_MAX`）；
   一旦命中或升档立即复位。理由：两小时的没票窗口里每 5 分钟查一次，只是给 12306 发无效请求。
3. **没票 ≠ 放弃**：`decide()` 只有在"有候选但怎么放宽都不满足"时才放弃；一条都没有时先扩搜（前两级），
   到第 2 级就转为长期等待 —— 昨天没票今天可能有票，这才是盯票的意义。
4. **单轮上限**：`WATCH_MAX_PER_ROUND`（默认 20）防止任务堆积时一次打满接口。

## 🧭 中转枢纽怎么挑（geo.py）

以前是 `hubs[:3]` —— 取列表里前三个站，和乘客从哪到哪毫无关系。现在按"是否顺路"筛：

| 判据 | 含义 | 例子（北京→上海） |
| --- | --- | --- |
| 沿线路进度 `t` | 枢纽在线路上的位置，要求 `0.12 ≤ t ≤ 0.92` | 天津 `t≈0.10` → 太近，排除（刚上车就下车） |
| 横向偏移比 | 垂直于线路的距离 / 全程，要求 ≤ 0.25 | 郑州 `0.43` → 方向不对，排除 |
| 绕行比 | `(起点→枢纽 + 枢纽→终点 − 全程) / 全程`，要求 ≤ 0.6 | 长沙 `1.09` → 兜底拦截 |
| 排序 | `绕行比 + 0.6×|t−0.5|` | 偏向"中段且几乎不绕路"的枢纽 |

坐标是**城市级近似值**（精确到 0.01°），只用于判断方向，不做测地计算；
认不出的城市会回退到原始顺序，不会因为查不到坐标就一个中转都不试。

## 🔀 多段中转（route.py）

以前最多只会拼两段（直达 + 一个枢纽）。现在支持 **A→h1→h2→B** 三段：

| 规则 | 取值 | 为什么 |
| --- | --- | --- |
| 换乘最短间隔 | 30 分钟（`TRANSFER_MIN_GAP_MIN`） | 接口不告诉你是否同站，取保守值；10 分钟那种拼出来也赶不上 |
| 换乘最长间隔 | 6 小时（`TRANSFER_MAX_GAP_MIN`） | 更久不如在中间城市过夜换方案 |
| 每段候选上限 | 25 班（`TRANSFER_SEG_KEEP`） | 三段全排列是 O(n³)，不剪枝会有几万组合 |
| 链候选上限 | 40 条（`TRANSFER_CHAIN_KEEP`） | 只留最早到达 / 最便宜的 |

**按城市拼、不按车站拼**：12306 的接口把站名归一到城市，在车站级别拼会 9×5 爆炸，
而且拼出来的"换乘"现实中未必同站。

**只在必要时才跑**：`max_transfers >= 2` 且盯票放宽到第 2 级（说明直达和一次换乘都没票）。
界面上「换乘」选「最多换 2 次（多段）」即开启。

实测（太原 → 厦门，2026-11-29，枢纽 武汉/合肥/南昌）：

```
请求 9 次 / 耗时 2.5 s / 可行链 40 条
2026-11-29 21:48-11:57 硬卧/硬卧/二等座 ¥622（换乘 2 次）
  V1398 太原→合肥 21:48-12:55 ｜ N221 合肥→南昌 18:50-01:21 ｜ D2361 南昌西→厦门北 07:20-11:57
```

**跨日要按绝对时间累加**：第一版用「同一天 + 必要时 +1 天」算总耗时，三段跨两天时会把
38 小时算成 14 小时。现在沿链推 `datetime`，`test_route.py` 里有一条「跨两天总耗时 > 24 小时」
专门锁死这个。

```bash
python test_route.py     # 23 条断言，全离线，不需要网络
```

### 仍然做不到的

- 换乘间隔是**固定窗口**，不知道是不是同站换乘、要不要出站（12306 不给这个数据）。
- 枢纽两两组合仍然是"先按顺路挑 3 个再组合"，不是全网搜索；真要全网搜就是图算法 + 时刻表了。
- 只算"最早到/最便宜"，不排出"在这座城市中转顺便吃个饭"这种人类约束。

## 📈 性能实测（bench_train.py）

数字来自容器内打真实 12306 接口，场景固定为 `北京 → 上海 2026-11-25`，复跑命令：

```bash
docker compose cp trainAI/bench_train.py train-ai:/app/bench_train.py
docker compose exec -T train-ai python bench_train.py
```

| 指标 | 数值 | 说明 |
| --- | --- | --- |
| 单次余票查询 | 75 ms（P50）/ 482 ms（P95） | 5 次采样，网络抖动明显 |
| 规划（3 枢纽） | 1 次请求 / 0.27 s / 84 候选 | 直达已可满足，未触发中转 |
| 规划（6 枢纽） | 5 次请求 / 2.34 s / 7785 候选 | 进入中转枚举 |

| 一次盯票 tick | 3 次请求 / 1.21 s | 修复前是 **135 次 / 54.6 s** |

### 那次 45 倍的修复

测量时发现一次 tick 要发 135 次请求、跑 54.6 秒。查下来是 `real_fetcher` 把城市展开成
同城车站逐个查：北京 9 个站 × 上海 5 个站 = 45 个组合。

但 12306 的余票接口**自己就把站名归一到城市**——查「北京南→上海虹桥」返回的仍是北京/北京丰台/
北京南 三个站的全部车次。所以那 45 次请求拿到的是 45 份一模一样的数据：请求数 ×45、
耗时 ×45、候选里全是重复项（候选数被灌到 33306，真实规模约 1.5 万）。

改为直接按城市查 + 按 `(车次, 席别, 日期)` 去重后：135 次/54.6 s → **3 次/1.2 s**。
新增 4 条断言锁死这个行为（`test_watch.py` 的第 11、12 组）。

### 已知开销

- 单次 tick 最短 3 次请求（直达 1 + 中转 2 段 × 1 枢纽）。放宽级别越高、日期窗口越大，请求数线性增长。
- 接口无官方配额说明，所以默认检查间隔 20 秒、退避上限 4×，宁可慢也不要把 IP 打进去。

## 🐳 部署（Docker）

```bash
docker build -t train-ai .
docker run -d --name train-ai \
  -p 8502:8501 \
  --env-file .env \
  -v "$(pwd)/cache:/root/.cache" \
  --restart unless-stopped \
  train-ai
```

- 镜像内已安装 `libgomp1`（onnxruntime 依赖），否则 fastembed 导入会失败。
- `/root/.cache` 挂载可缓存 bge-small-zh 模型，避免每次重启重新下载。
- `stations.json` 首次运行自动抓取并落盘，不进镜像。
- 与个人事务项目同时部署时使用根目录的 `docker-compose.yml`；公网访问见 `DEPLOY.md`。
